## БЛОК 1: Telegram API — доступ к данным каналов

### Вывод: используем MTProto через Pyrogram, Bot API не подходит для чтения истории

**Два способа читать данные Telegram-канала:**

| | Bot API | MTProto (Pyrogram/Telethon) |
|---|---|---|
| Читать новые посты | ✅ Webhook/polling | ✅ |
| Читать историю (старые посты) | ❌ Нет | ✅ `get_chat_history()` |
| Нужно ли вступать в канал | ✅ Да (для ботов) | ✅ Да (userbot должен быть в канале) |
| Читать публичный канал по username | ✅ Ограниченно | ✅ Полный доступ |
| Rate limits | 30 msg/sec | FloodWait — от секунд до часов |

**Ключевой факт:** Pyrogram `get_chat_history()` читает публичный канал по username без вступления, но FloodWait может заблокировать аккаунт на часы при агрессивном скрейпинге. Источник: Pyrogram docs, GitHub issues.

**Решение для нашего сервиса:**
- Канал владелец сам добавляет нашего бота как admin (read-only)
- Бот читает контент через Bot API webhook (новые посты) + MTProto одноразово (история)
- При регистрации делаем batch import истории (1 раз, медленно, с паузами)
- Новые посты — через Bot API webhook (мгновенно, без лимитов)

**Rate limits Bot API (фактические, после обновления Jan 2025):**
- 1 msg/sec в одном чате
- 20 msg/min в группах
- 429 ответ с `retry_after` в секундах при превышении
- Для READ операций (getUpdates, getChat) — отдельные мягкие лимиты

## БЛОК 2: Трекинг конверсий в подписчиков

### Вывод: точный трекинг ВОЗМОЖЕН через уникальные invite links

**Механизм (подтверждено Telegram Bot API docs):**

1. Наш бот (admin канала) создаёт уникальную invite link через `createChatInviteLink`
2. Эта ссылка встраивается в каждую веб-страницу: "Открыть в Telegram"
3. Когда пользователь переходит по ней и вступает — Telegram это фиксирует
4. Через `messages.getChatInviteImporters` (MTProto) или Bot API `ChatInviteLink` можно получить список вступивших по конкретной ссылке

**Структура Bot API `ChatInviteLink`:**
```json
{
  "invite_link": "https://t.me/+abc123",
  "creator": {...},
  "creates_join_request": false,
  "is_primary": false,
  "is_revoked": false,
  "member_limit": null,
  "pending_join_request_count": 0
}
```

**Схема трекинга:**
```
Веб-страница поста → уникальная invite link (1 ссылка на весь канал)
                   → статистика: clicks_total из аналитики страниц
                   → members_joined: delta getChatMemberCount по времени
```

**Честность метрики:** invite link даёт точный счёт вступивших по ней. Это ТОЧНЫЙ трекинг, не приблизительный. Источник: `messages.getChatInviteImporters` в MTProto API.

**Требование:** наш бот должен быть admin канала. Это обязательное условие для создания invite links через Bot API.

## БЛОК 3: SEO — риски и механика

### Вывод: duplicate content риска нет, если AI добавляет уникальную ценность

**Факт из Google официальных источников:**
> "Google doesn't directly penalize duplicate content unless it's designed to manipulate rankings."
> Источник: Google Search Central Blog (2008, подтверждено в 2025 Spam Update)

**Что реально происходит с "клон-страницами":**
- Google фильтрует дубли, показывает "авторитетную версию"
- Thin content (страница без уникальной ценности) — вот реальная угроза
- September 2025 Spam Update: cookie-cutter pages без уникальности получили penalties

**Наше решение (критически важно):**
AI должен создавать НЕ клон поста, а **статью на основе поста** с добавленной ценностью:
- Заголовок: SEO-оптимизированный, не просто первые слова поста
- Intro paragraph: контекст и summary поста (200-300 слов)
- Post content: оригинальный текст + структурированная разметка
- Conclusion + CTA: "Читать больше в канале @name"

Это делает страницу УНИКАЛЬНОЙ, не клоном.

**Canonical tag стратегия:**
- НЕ ставить canonical на t.me/channel/postid — это убьёт индексацию нашей страницы
- Ставить canonical на НАШУ страницу (self-referential canonical — стандартная практика)

**Schema.org: BlogPosting, не SocialMediaPosting**
- `BlogPosting` — подтип `Article`, лучше поддерживается Google rich snippets
- `SocialMediaPosting` — технически точнее, но Google меньше использует для rich results
- Решение: `BlogPosting` с полями `headline`, `author`, `datePublished`, `image`, `description`

**Индексация:**
- IndexNow (Bing + Yandex): мгновенно (часы), до 10K URL за запрос. Google НЕ поддерживает.
- Google: sitemap.xml + ждём естественного crawl. Google Indexing API только для JobPosting/VideoObject.
- Стратегия: IndexNow для Bing/Yandex при публикации + sitemap обновляется автоматически

## БЛОК 5: Инфраструктура и масштабирование

### Вывод: Next.js ISR + PostgreSQL FTS + Vercel/Railway — достаточно до 10K каналов

**Расчёт объёма:**
```
1000 каналов × 500 постов = 500K страниц
10K каналов × 500 постов = 5M страниц
```

**SSG vs SSR vs ISR:**
- SSG (pre-build all): 500K страниц × 1 сек сборки = нереально (139 часов)
- SSR (каждый раз с нуля): медленно для SEO (Core Web Vitals)
- **ISR (Incremental Static Regeneration)**: рендерим по запросу, кэшируем. Первый visitor = SSR, все следующие = статика. **Это наш выбор.**

**Хостинг:**
- Vercel Pro: $20/мес + $0.15/GB bandwidth after 1TB. Для MVP — идеально, ISR из коробки.
- Railway: $5-20/мес, больше гибкости, нужно настраивать ISR самостоятельно.
- VPS (Hetzner CCX23): $40/мес, полный контроль, для масштаба лучше.

**База данных:**
- PostgreSQL FTS: достаточно для 500K документов. Elasticsearch нужен только при >5M + complex queries.
- Основные таблицы: `channels`, `posts`, `pages`, `analytics_events`
- Индексы: GIN на tsvector колонки для полнотекстового поиска

**Очередь:**
- BullMQ (Redis) для обработки: import истории, генерация AI-метаданных, ping IndexNow
- 1 worker может обрабатывать ~100 постов/мин с учётом AI latency

**CDN для медиа Telegram:**
- Telegram медиа (фото/видео) не хранится вечно на их серверах
- Решение: при создании страницы — скачать медиа, сохранить в Cloudflare R2 или Supabase Storage
- Cloudflare R2: $0.015/GB хранения, $0 egress. **Лучший выбор.**

**Расчёт стоимости инфраструктуры (1000 каналов):**
```
Vercel Pro:          $20/мес
PostgreSQL (Neon):   $19/мес (Pro plan, 10GB)
Redis (Upstash):     $10/мес
Cloudflare R2:       ~$5/мес (медиа хранение)
OpenAI API:          ~$6/мес
----------------------------------
ИТОГО:               ~$60/мес
```

При тарифе Hobby 350₽/мес (~$4) × 1000 каналов = $4000/мес выручка. Маржа огромная.

## БЛОК 7: Правовые риски

### Вывод: легально при наличии согласия владельца канала

**Telegram ToS — анализ:**
> "access to user-generated content for any purpose other than ordinary, legitimate, and intended use of the Telegram platform as its user is prohibited"
> Источник: core.telegram.org/api/terms

**НО:** TGPages работает и не заблокирован. Почему?

**Ключевое различие:**
- Запрещено: scraping без разрешения, AI обучение
- Разрешено: создание legit Telegram Bot/App с явного согласия пользователя

В нашем случае:
1. Владелец канала САМИ регистрируются на сервисе
2. Они ДОБРОВОЛЬНО добавляют нашего бота как admin
3. Это explicit consent от правообладателя контента
4. Контент принадлежит АВТОРУ, не Telegram. Автор разрешил.

**Авторские права:**
- Пост в Telegram принадлежит автору/каналу
- Владелец канала регистрируясь на сервисе даёт нам лицензию на публикацию
- Нужен явный пункт в ToS: "Регистрируясь, вы предоставляете нам право публиковать..."

**152-ФЗ:**
- Мы не храним личные данные подписчиков (только владельцев каналов)
- Email + имя владельца = персданные → обработка по 152-ФЗ обязательна
- Нужно: политика конфиденциальности, согласие на обработку, хранение на серверах РФ

**Хранение данных:**
- Для РФ-пользователей данные должны храниться на серверах в РФ (152-ФЗ)
- VDS/VPS в РФ (Hetzner Nuremberg → Selectel/Timeweb для прода)
- Или: отдельная БД для RU-данных на RU-серверах
